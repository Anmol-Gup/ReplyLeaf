# Replyleaf: WhatsApp AI assistant for small businesses (multi-tenant)

Next.js (App Router, TypeScript) on Vercel + Supabase (Postgres, pgvector, Auth). Small businesses connect a WhatsApp number; an AI assistant (Gemini or OpenAI, chosen per client) answers customers using only that business's knowledge base. Owners manage everything from a dashboard.

**Status: all 6 stages are built and unit-tested (120 tests).** Nothing has been run against real Meta, Supabase, Gmail or AI-provider accounts yet; see [What is not verified yet](#what-is-not-verified-yet).

> **Real clients can only onboard after Meta approves your app as a Tech Provider.** The Embedded Signup flow (Stage 6) is written but only works for people with a role on your own Meta app until App Review is passed. Until then, connect numbers yourself with `npm run create-client`.

## How it works
1. `POST /api/webhooks/whatsapp` verifies `X-Hub-Signature-256` (HMAC-SHA256 of the **raw** body, constant-time compare). Invalid signature: 401. `GET` answers Meta's verify handshake.
2. It **stores the messages first** (quick DB-only step) via the SQL function `record_inbound_message`: one transaction upserts the contact and conversation, inserts the message (`UNIQUE(wa_message_id)` dedupes Meta retries) and queues it in `pending_messages`. If storing fails the route returns 500, so Meta retries.
3. It returns `200` and does the slow work in `after()` (Next.js; on Vercel backed by `waitUntil`, so the function stays alive up to `maxDuration` = 60s).
4. **Batching:** each inbound message pushes the conversation's `batch_due_at` to now + 4s. After waiting, a worker claims the conversation with one atomic UPDATE (`claim_batch`; the row lock lets only one concurrent worker win), builds one prompt from all pending messages, sends one reply, then `complete_batch` removes the handled rows. Messages that arrive during the reply cause another loop.
5. **Recovery:** the claim sets a lease (120s). If a worker crashes the lease expires and the sweep (`find_due_batches`) re-processes the batch. The sweep runs after every webhook request and from `/api/cron/sweep`. Delivery is at-least-once: a crash between sending and completing can produce a duplicate reply, which is preferred over silence.
6. `generateReply()` (`lib/ai/generate-reply.ts`) calls the client's provider (Gemini or OpenAI adapter in `lib/ai/providers.ts`) and asks for JSON. The output is parsed and validated with Zod; on failure it retries once, then throws. Nothing downstream sees unvalidated output. Input/output tokens are stored on the message and in `usage_events`.

Rules enforced in code: human takeover (`human_active`) keeps the bot silent; auto-handoff on `intent = human_needed` or two failed answers in a row; free-form sends only inside the 24-hour window (otherwise recorded as `blocked` and shown as a warning); media-only messages get a "please send text" reply with no AI call; per-customer limit of 30 messages/hour; per-client monthly reply cap (`clients.monthly_message_cap`) checked before each model call; any failure writes an `admin_alerts` row, emails the admin and sends the customer a safe fallback.

**Prompt-injection stance:** the system prompt holds only our rules and the owner's knowledge. Customer text goes only inside `<customer_messages>` tags in a user turn (our closing tag is stripped from it), is labelled untrusted, and the model has no tools, so it cannot read other customers' data or change settings.

**Deviation from the spec:** the model JSON has one extra field, `answered` (boolean). It is the signal needed for "two failed answers" handoff and for logging unanswered questions. Remove it from `lib/ai/schema.ts` if you disagree.

### Email notifications: one daily summary (migration 0014)
By default a business gets **one email a day** (`/api/cron/daily-digest`, 03:45 UTC, which is 09:15 IST) listing the new contacts, project enquiries, appointment requests and tickets from the last 24 hours, plus what is still waiting (appointment requests to confirm, open tickets with the urgent ones counted, chats waiting for a person, lead follow-ups due). Sections follow the notification switches, nothing is sent on a day with nothing new and nothing waiting, a business gets at most one per day (running the job twice is harmless), and businesses without an active subscription are skipped. If the send fails the slot is given back so the next run retries. The summary goes to the main address plus the extra recipients.

**Still sent immediately:** a chat that needs a person (Human handoff), the "your AI key needs attention" email, the "WhatsApp connected" email, and every billing email. Owners can switch back to **an email for each one as it happens** under Settings > Email notifications > How often (`notification_settings.delivery`). Businesses with no settings row yet count as daily. Check that your Vercel plan allows this many cron jobs, or call the route from any scheduler with `Authorization: Bearer $CRON_SECRET`.

### Billing: Stripe subscription, 999 INR / month (migration 0013)
One plan, **WhatsApp AI Assistant, ₹999 per month**, one subscription per business, no trial, no usage billing. The subscription covers access to Replyleaf; the business pays its own AI provider (its own key) and Meta's WhatsApp charges separately, and we never bill for AI or messages. Stripe is the source of truth: webhooks copy its state into the database, **nothing is granted because of a browser redirect or anything the browser sends**, and access is decided on the server from the stored state.

**Switching it on.** Billing is enforced only when `STRIPE_SECRET_KEY` and `STRIPE_PRICE_ID` are set; without them the app behaves as before (every feature available). Businesses that existed when migration 0013 ran are **exempt** (`clients.billing_exempt = true`) so nothing breaks; new businesses are not. Grant or remove a complimentary account in SQL: `update clients set billing_exempt = true where id = '...'`.

**Stripe Dashboard setup (test mode first)**
1. Create a Product "WhatsApp AI Assistant" with ONE recurring Price: 999 INR, monthly. Put its id in `STRIPE_PRICE_ID` and your keys in `STRIPE_SECRET_KEY` (server only).
2. Webhooks > Add endpoint: `https://YOUR-DOMAIN/api/billing/webhook` with events `checkout.session.completed`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`. Copy the signing secret into `STRIPE_WEBHOOK_SECRET`.
3. Settings > Billing > Customer portal: switch on update payment method, invoice history and cancel subscription (cancel at the end of the billing period is the default we use). Save.
4. Settings > Billing > Retries: use Smart Retries or a schedule that ends within about 7 days, and set "if all retries fail" to leave the subscription **past due** (not cancel it): the app gives 7 days of grace itself.
5. Run `supabase db push` (migration 0013) and deploy. The daily job `/api/cron/billing-reconcile` (05:00 UTC, in `vercel.json`) re-checks stale subscriptions; check that your Vercel plan allows this many cron jobs, or call the route from any scheduler with `Authorization: Bearer $CRON_SECRET`.

**What the customer sees.** Dashboard > Billing: plan and price, status, next payment date, current period, payment history (with Stripe's invoice links), Subscribe, Manage billing (Stripe's portal) and Cancel (at the end of the paid period). A banner on every page warns about a failed payment (with the days left) or an inactive subscription. The Billing page, settings, viewing data and **Export my data** (`/api/account/export`) always work.

**Access rules (`lib/billing/access.ts`, one function, unit-tested)**

| State | Access |
|---|---|
| Active, within the paid period (a plain renewal gets 24h of slack while the payment settles) | Full |
| Past due, inside the 7-day grace (fixed at the FIRST failure; retries do not extend it) | Full, with a warning banner |
| Past due, grace over | Restricted |
| Cancelled at period end, period not over | Full until the paid-through date |
| Cancelled and ended, unpaid, incomplete, paused, or no subscription | Restricted |

**Restricted means:** no AI replies, no new leads, appointments or tickets from WhatsApp, no automation or background work for that business (the batch worker skips it, the daily check ignores it), and the paid dashboard actions are blocked: sending WhatsApp messages from the dashboard, knowledge-base changes, and appointment or ticket updates that message the customer. Customers are not sent any message; messages received meanwhile are stored (the owner can read them) but are **not replayed** after payment recovers, so nothing is answered twice. Token refresh and data retention still run for everyone. **Nothing is ever deleted** for non-payment. When Stripe confirms payment, access returns immediately.

**Webhook handling (`lib/billing/service.ts`).** The signature is verified over the raw body (5 minute window) before anything is parsed. Every event id is processed once (`claim_stripe_event`); a failure answers 5xx so Stripe retries. Subscription state is always **re-read from Stripe's API** instead of trusted from the event, so stale and out-of-order events cannot overwrite newer state; an older subscription can't overwrite a live one; the tenant comes from Stripe metadata that we set at checkout and is cross-checked against the stored customer. Each billing email (first subscription, failed renewal, action required, grace reminder, cancellation, ended, expired, recovered; renewals optional) is sent once per key. Checkout reuses a still-open session instead of creating another, and an active customer is sent to the billing page.

**Testing it (Stripe test mode, no real money)**
- *First payment:* Billing > Subscribe, pay with `4242 4242 4242 4242`, any future date and CVC. Locally run `stripe listen --forward-to localhost:3000/api/billing/webhook` and use the printed signing secret as `STRIPE_WEBHOOK_SECRET`. Access starts when the webhook (or the post-checkout read from Stripe) confirms it.
- *Renewal failure and grace:* Dashboard > Billing > Test clocks: create a clock, create the customer on it by subscribing with the card `4000 0000 0000 0341` (it attaches, but later charges fail), then advance the clock past the first renewal. You get `invoice.payment_failed`, the subscription becomes past due, the banner and the email appear, and replies continue. Advance 7 more days: access stops, the reconcile job (`GET /api/cron/billing-reconcile` with your `CRON_SECRET`) sends the expiry email.
- *Recovery:* in the portal, or by paying the invoice, with a working card. `invoice.paid` makes it active and clears the grace.
- `stripe trigger ...` fixtures carry no business id, so they are acknowledged and ignored by design. The automated tests cover all 16 scenarios without Stripe (`tests/billing*.test.ts`, `supabase/tests/billing_smoke.sql`).

**India.** Stripe INR recurring payments require the customer to authorise a mandate. Before going live, confirm in Stripe that your account can take recurring INR payments, which payment methods support recurring in India, and review the mandate and notification rules. The billing page states ₹999 per month and that it renews automatically; the subscription only starts once Stripe confirms the authorisation, and we do not promise renewal beyond what Stripe confirms.

### AI keys: bring your own, or the platform's (migration 0012)
Each business has an AI mode (`clients.ai_mode`):
- **`byok` (bring your own key), the default for businesses that sign up and connect through Embedded Signup.** The business pastes its own Gemini or OpenAI key in Settings > AI. The key is checked with the provider (a free "list models" call), then **encrypted with AES-256-GCM and stored in `client_secrets.ai_api_key_enc`**, which owners cannot read through the API (RLS with no policy). Only a status and the last four characters are shown. The provider bills the business directly, and its usage still shows on the Usage page. The monthly reply cap is not applied (it exists to protect the platform's AI bill). In this mode the platform's keys are **never** used, even as a fallback.
- **`platform`**: the platform's key is used and the platform pays, with the monthly reply cap applied. Existing clients and clients made with `create-client` are on this. There is no screen to grant it: change `clients.ai_mode` in the database. A business on it can switch itself to its own key by saving one.
- **If a business on its own key has no usable key, or the provider refuses it,** the assistant is off for that business: customers get a short "our team will reply" message, the chat goes to Human handoff (source "AI key missing or not working") so nothing is lost, the key is marked invalid, and the owner is emailed once a day. Saving a working key hands those chats back to the assistant automatically. Quota and outage errors are not treated as a bad key.
- **Not built yet (Mode B extras):** paid usage for the platform's AI, credit balances and quotas per business, and Anthropic (Claude) as a provider. Claude would need `@anthropic-ai/sdk`, which is not installed. The two columns that decide behaviour (`ai_mode`, and the key status) are where credits would plug in.
- **Knowledge-base search embeddings still use the platform's Gemini key** for every business (a small cost, not billed to them).

### Appointment requests, project enquiries and settings (migration 0010)
There is no calendar connection. The assistant never says anything is booked or confirmed, and working days and hours are information only (it never promises a free slot).

**One engine, guarded on the server.** The model returns `intent` (question, appointment_request, project_enquiry, human_needed, other), the details collected so far, a `workflow` state (flow + stage) and an `action`. The action is only a proposal: `lib/workflow.ts` saves a request only when the feature is on for that business, the previous turn showed the customer a summary (stored in `conversations.workflow_state`, stale after 48 hours), the customer's latest message confirmed it, and the required fields validate. Otherwise nothing is saved and the customer is asked to confirm again. The request is saved BEFORE the "submitted" reply is sent; if saving fails the customer is told our team will follow up, the admin is alerted and a person takes over. Dates must be real dates from today to a year ahead.

- **Appointments** (`appointments`, statuses pending, confirmed, reschedule_requested, rejected, cancelled, completed): the assistant collects purpose, preferred date and time, name (the WhatsApp number is already known), optional online or in person, time zone and notes, one or two questions at a time, shows a summary, and saves a `pending` request after the customer confirms. A customer can have SEVERAL open requests (a different purpose, date or time is a new request); the same request while it is still open is stored once and the customer is told it is already with the team. The owner is emailed. On the Appointments page the owner confirms (with the final date and time), rejects (with a reason), asks to reschedule (the alternative is sent to the customer), cancels, marks completed, and keeps internal notes (never sent to the customer). The customer is told on WhatsApp when the 24-hour window is open, otherwise by email if we have their address; if neither works the page says so and shows the text to send by hand. A customer's reply to a reschedule request is handed to a person.
- **Tickets** (`tickets`, statuses open, in_progress, waiting_on_customer, resolved, closed; migration 0011): when a customer reports a problem ("my order didn't arrive") the assistant asks only what the team needs (what went wrong, an order or booking reference, what they would like), shows a summary, and logs a ticket after the customer confirms. It never promises a refund, replacement or resolution time. Priority is `high` only when the customer says it is urgent (the email says URGENT). The Tickets page has filters, search, an assignee (typed name or email), status, internal notes, and an optional "tell the customer" when you resolve or close it (WhatsApp if the window is open, otherwise email). The same open issue twice is stored once; after it is resolved the same problem can be raised again. A ticket is not a handoff: the assistant keeps replying.
- **One customer, many records:** the contact page shows an Activity list of every lead, appointment, ticket and handoff for that person, and the assistant is told how many open requests, tickets and enquiries the customer already has so it can acknowledge them.
- **Leads** (`leads` + `lead_requirements`, statuses new, qualified, contacted, proposal_sent, negotiation, won, lost): relevant questions only, optional ones may be skipped, a summary is confirmed, then the lead is saved with structured requirements. A lead is `qualified` only when both budget and timeline are known, otherwise `new`. The same enquiry sent twice is stored once. The Leads page has search, status filters, the conversation, requirements, internal notes, a follow-up date, and Copy / Download of the project brief (which leaves out internal notes).
- **Settings** (Settings page): per business, appointment requests (on/off, working days and hours, length, notice, instructions), project enquiries (on/off, services, custom questions, budget ranges, instructions), tickets (on/off, categories, response time, instructions), human handoff (on/off, availability, response time, extra escalation cases) and email notifications (main address, up to 5 more, switches for appointments, leads, tickets and handoffs). Stored in `clients.workflow_settings` and `notification_settings`; bad values fall back to defaults. If handoff is off the assistant never promises a person. Recipients are shared by all three workflows (there are no per-workflow recipients).
- **Emails** go through `notifyOwner`, which applies the recipients and switches, sends to each address separately (one bad address does not block the others) and alerts the admin only if nobody could be emailed. Each is sent once: a retried webhook finds the open request or lead and sends nothing.
- **Cost note:** the workflow rules roughly double the input tokens of each AI call compared with a plain Q&A prompt.
- **Checks:** `npm run eval:flows` runs the multi-turn flows (appointment, enquiry, ticket, a prompt-injection attempt, booking link, appointments off) against a real model with the same server rules. `supabase/tests/workflows_smoke.sql` (appointments, leads, tickets, notification settings), `handoff_smoke.sql`, `ai_keys_smoke.sql` (the key can never be read back) and `billing_smoke.sql` test the SQL against a throwaway Postgres.

### Human handoff
A handoff silences the assistant for ONE conversation (`conversations.handling = 'human_active'`; other chats are untouched) and writes a `handoff_requests` row: why it happened, a short model-written summary, who has it, internal notes, and a status of `requested` > `assigned` > `human_active` > `resolved` (migration 0009, functions `create_handoff` and `set_handoff_status`). It starts when the customer asks for a person or is upset or has a sensitive request (the model sets `human_needed`), after two unanswered questions in a row, when a customer wants to book and no booking link is set, or when the owner clicks Take over. The owner is emailed once per handoff (a retried webhook finds the open request and sends nothing). Only one handoff can be open per conversation.

The **Human handoff** page lists them with filters and search. Per request: open the chat to reply (replies go out over WhatsApp inside the 24-hour window; after it closes the page says so and nothing is sent), Take over (assigns it to you), Assign (a typed name or email, or "Assign to me"; there are no team accounts yet), Mark resolved (the assistant STAYS silent), Resume assistant (resolves it and switches the assistant back on), and an internal note that is never sent to the customer. `supabase/tests/handoff_smoke.sql` checks the SQL against a throwaway Postgres.

### CRM, booking link and owner alerts
- Every person who messages becomes a contact. A contact's first reply flips it from `new` to `lead` and emails the owner (once, guarded by an atomic SQL update).
- Names/emails the model extracts are guesses. `apply_contact_details` fills **empty** fields only; a different value goes to `contacts.suggested` for the owner to confirm in the dashboard. Emails must pass Zod validation first; junk like "n/a" is dropped.
- Booking: the assistant never books anything itself. With a `booking_link` it shares the link. With no link and appointment requests switched on (the default) it collects an appointment REQUEST (see below). With no link and requests switched off, a person takes over.
- Owner emails (new lead, conversation needs a human) go to `clients.owner_email`; failures go to `ADMIN_ALERT_EMAIL` (the first alert of a kind per client per 10 minutes is emailed, the rest stay in `admin_alerts`). Email uses nodemailer + Gmail SMTP behind the `Mailer` interface in `lib/email/mailer.ts`; to swap providers, write another implementation there. Emails are plain text and subjects are forced to one line.
- Bookkeeping that fails *after* the customer already got their reply is alerted but never triggers the "something went wrong" fallback.

### Owner dashboard (`/dashboard`)
Conversations (takeover / hand back / reply), leads, appointments, tickets, human handoff, contacts (edit, confirm or dismiss suggestions, delete a person's data), knowledge base (core text holds the business description, hours and key prices), settings (business name, booking link, AI provider, alert email), usage (tokens, monthly cap).
- **Login:** Supabase Auth email + password, no social login.
- **Sign-up** (`/signup`, controlled by `SIGNUP_MODE`): `open` (default) lets anyone sign up and, after confirming their email, connect their own WhatsApp through Embedded Signup, with no manual approval; `approval` is an optional gate where accounts only see a "you're on the list" page until you approve them on `/admin/signups`; `off` removes public sign-up. Anyone linked to a business counts as approved, and `create-owner` logins are approved automatically. The `/onboarding` page and its callback endpoint both refuse unapproved accounts. "Approved" is a flag in the login's `app_metadata`, which users cannot edit, so no database change is involved.
- **The sign-up journey:**
  1. They submit the form and a dialog says a **verification email** was sent.
  2. They get Supabase's confirmation email (branded, see below) and click the button. It opens our **`/auth/confirm`** page, which verifies the address on the server by itself (a script submits the page once in a real browser, so the person clicks only the email link, while email scanners that merely fetch the page cannot use up the one-time link; without JavaScript a button is shown), and then **`/verified`** shows "Your email is verified". An invalid or expired link shows "This link has expired" or "isn't valid" with a form to **send a new link**. Signing in before verifying says "Please verify your email first" with the same resend option. Links from Supabase's *default* template (which end in `/#access_token=...`) are also caught: a tiny script in the page `<head>` redirects them to the same result pages before anything is drawn (no flash of the home page), and the token in the address is dropped and never used.
  3. (Only with `SIGNUP_MODE=approval`.) They sign in and land on the waiting page. **At that moment, once**, two separate branded emails go out: "You're on the list" to the user, and "New sign-up waiting for approval" to `ADMIN_ALERT_EMAIL` with a button to the approval page. Sending after verification means unverified or mistyped addresses never reach your inbox.
  4. You approve them at **`/admin/signups`**. They get an "Your access is ready" email.
- **Approval page** (`/admin/signups`): lists everyone waiting (verified people first), with **Approve** (only enabled once they have verified their email) and **Reject** (deletes the account; it refuses anyone who already has a business). Only platform admins can open it; everyone else gets a 404. Create your admin login once with `npm run create-admin -- you@example.com`: no sign-up and no email verification, and it prints a strong random password once in your terminal (or set your own with `ADMIN_PASSWORD='12+ chars'`). Then sign in on the normal `/login` page. To promote an account that already exists, use `npm run make-admin -- you@example.com`. Admins sign in on their own page, **`/admin/login`** (no sign-up link; a correct password for a non-admin account is refused and sets no session), and are returned to the page they were going to. Both lists are paginated (10 per page). Admins also have an "Admin: sign-ups" link in the dashboard menu. Password fields everywhere have a show/hide toggle. The commands `npm run list-signups` and `npm run approve-user -- <email>` still work too.
- **Branded emails:** one shared HTML layout (`lib/email/html.ts`) is used for the waiting-list, new-sign-up and approved emails, each sent with a plain-text twin; all dynamic text is escaped. The **verification email is sent by Supabase**, not by this app, so its look is installed in Supabase. The button points to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`, so **Supabase's Site URL must be this app's URL** (the same as `APP_URL`). Until you install this template, Supabase's default email is used (it still works, see above). Either run `SUPABASE_ACCESS_TOKEN=sbp_... npm run push-email-template` (create the token at supabase.com/dashboard/account/tokens; it changes only the confirmation email's subject and body, and must not be put on Vercel), or run `npm run email-templates` and paste `supabase/templates/confirm-signup.html` into Authentication > Emails > Templates > Confirm signup.
- **Sign-up protection:** email confirmation (turn it on, see Setup), Supabase's built-in rate limits, a hidden honeypot field, and the approval step. If the address already has an account the form says so ("An account with this email already exists", with links to sign in or resend the verification link). That is friendlier, but it means the form can be used to check whether an email is registered; Supabase's rate limits slow that down. To hide it again, remove the `isExistingAccount` check in `app/signup/actions.ts`. There is no CAPTCHA.
- **Creating an owner by hand** still works: `CLIENT_ID=<uuid> OWNER_LOGIN_EMAIL=... OWNER_PASSWORD='12+ chars' npm run create-owner`.
- **Sessions** use plain supabase-js (no extra package): the login action stores the tokens in httpOnly cookies, `proxy.ts` refreshes them, and every page re-verifies the user with Supabase (`requireClient()` in `lib/auth/session.ts`).
- **Tenant isolation, two layers:** page reads use a client carrying the owner's own JWT, so RLS applies. Writes (server actions) use the service role but always filter by the `client_id` derived from the verified membership, never from form input. `supabase/tests/rls_isolation.test.sql` is a pgTAP test of the isolation rules (`npx supabase test db`, needs Docker).
- **Human reply:** take over a conversation first (the assistant stays silent while you handle it). Replies outside the 24-hour window are blocked, recorded as "NOT SENT", and shown with a clear warning.

### Knowledge base at scale
- **Two layers.** *Core knowledge* (`clients.kb_text`, max 8,000 chars) is always in the prompt: hours, headline prices. *Documents* hold everything else; for each customer message only the most relevant chunks are added (`<retrieved_knowledge>`).
- **Adding documents** (dashboard > Knowledge base): paste text or upload **.pdf, .docx, .txt** (also .md), up to 2 MB. The text is extracted, shown to the owner for editing, and **nothing is searchable until the owner confirms**. Drafts can be discarded.
- **Chunking** is by markdown headings (`# Policies > ## Cancellations` keeps its path in the chunk), with long sections split at paragraph/sentence boundaries (`lib/kb/chunk.ts`). Word headings become `#` headings on import.
- **Hybrid search** (`search_kb` SQL function): full-text rank and vector rank merged by reciprocal rank fusion, active documents of one client only. Embeddings: Gemini `gemini-embedding-2`, 768 dimensions, one model for every client regardless of their chat provider (so `GEMINI_API_KEY` is needed for search). If embedding fails, chunks are stored without vectors and keyword search still works; the owner can press *Re-index* later.
- **Version history:** every publish keeps the full text (`kb_document_versions`); restoring creates a new version, so history is never rewritten. Archived documents stop being searched.
- **Unanswered questions:** when the model says it could not answer (`answered: false`), the customer's question is logged and listed in the dashboard so the owner can add the answer.
- **File parsing uses no extra packages** (`lib/kb/extract.ts`, built on `node:zlib`). `.txt`, `.md` and `.docx` are reliable. **PDF is best effort:** it reads simple text PDFs, and refuses (with a clear message, storing nothing) scanned PDFs and PDFs whose fonts use custom encodings, which includes many PDFs exported from Word or Google Docs. For robust PDF support, add a parsing package such as `unpdf` and replace `extractPdf`. It was not added because the project rules say to ask before adding dependencies.
- Embedding token usage is not tracked (the embeddings API does not report it).

### Onboarding, privacy and operations (Stage 6)
- **Embedded Signup v4** (`/onboarding`, callback `POST /onboarding/callback`): a signed-in owner without a business sees a "Connect WhatsApp" button that opens Meta's popup (this uses Meta's JS SDK only to connect a number; owners never log in with Facebook). The browser sends the one-time `code` (valid ~30s) plus `waba_id` and `phone_number_id`; the **server** then (1) exchanges the code for a business token, (2) checks that token can read that phone number (so nobody can claim someone else's number), (3) subscribes our app to the customer's WABA, (4) registers the number with a 6-digit PIN, (5) stores the token and PIN **encrypted** (AES-256-GCM) together with the token's expiry, (6) goes live and emails the owner. The request is protected by a signed, 30-minute, per-user `state` token and requires JSON. Needs `NEXT_PUBLIC_META_APP_ID` and `NEXT_PUBLIC_META_ES_CONFIG_ID`; without them the page tells the user to contact you.
- **Coexistence (keep using the WhatsApp Business app):** the popup is launched with `featureType: "whatsapp_business_app_onboarding"`, so an owner can connect a number that is still in the WhatsApp Business app (app version 2.24.17+) and keep using the app. For such a number Meta reports only the WABA (`FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING`), so the server looks the number up (`GET /{waba}/phone_numbers`), **skips `/register`** (already registered, no PIN) and instead requests the contacts and history sync Meta requires within 24 hours (`POST /{phone}/smb_app_data`; each can be requested once; the resulting `history` / `smb_app_state_sync` webhooks are accepted and ignored for now). When the owner replies from the app, Meta sends `smb_message_echoes`; we store it as a human message and the assistant steps aside for that chat (a `human_active` handoff, migration 0016). The owner switches it back on with "Resume assistant". **In the Meta app's webhook settings subscribe to `account_update`, `messages`, `smb_message_echoes`, `history` and `smb_app_state_sync`**, and make sure the Embedded Signup configuration allows the "WhatsApp Business app" onboarding. Limits: 20 messages/second, group chats are not synced, and the owner must open the Business app at least every ~14 days to stay connected. Not yet verified against Meta.
- **Resumable and duplicate-proof:** the client row is created first and every step records where it got to (`clients.onboarding_step`). A failure marks it `failed` with that step, the owner sees a plain-language reason and **Reconnect** (a new popup code is needed because codes are single-use), and the retry **resumes the same row**. A double click is refused while a flow is running (and a crashed flow becomes resumable after 2 minutes). Rules, all in `lib/onboarding-plan.ts`: one client per login; a WABA or phone number belongs to exactly one client, so connecting one linked to a *different* client is rejected (database unique indexes back this up, including under races).
- **Real status in the dashboard** (Overview and Settings): `pending` (our steps are done, waiting for Meta; or still running), `connected` (Meta confirmed), `failed` (with the reason), or nothing for clients you created manually. The confirmation is the **`account_update` webhook** (`PARTNER_ADDED`), handled by the same signature-verified webhook route. It carries `waba_info.waba_id` but no phone number, so it is matched to the client by WABA. It can arrive before our callback has finished, so events are stored and checked. `PARTNER_REMOVED` marks the client failed and alerts the admin.
- **Token lifecycle (60-day tokens):** `/api/cron/token-refresh` runs daily, finds tokens expiring within 14 days, and refreshes them with the documented `fb_exchange_token` grant (`set_token_expires_in_60_days=true`). A failed refresh emails you; a token that has already expired marks the client `failed` ("reconnect") and emails you. **Where Meta's docs are unclear (so verify live):** (a) whether the Embedded Signup code exchange returns `expires_in`; if it does not, we assume 60 days and record `wa_token_expiry_assumed = true`; (b) whether the refresh grant, documented for system-user tokens, works for Embedded Signup business tokens. If (b) fails, customers must reconnect every 60 days (the dashboard and your email tell them), so test it early (checklist below). The old token keeps working until its own expiry; we never revoke it.
- **Data deletion on request:** owners use the button on a contact's page, or `POST /api/privacy/delete {"phone": "+91..."}` with their dashboard session. Admins can call it with `Authorization: Bearer $ADMIN_API_KEY` and a `clientId` (disabled unless `ADMIN_API_KEY` is set). It deletes the contact and, by cascade, their conversations, messages, pending batches, leads, appointments, tickets and logged questions for that one client.
- **Retention job** (`/api/cron/retention`, daily, SQL function `run_retention`): message **content** blanked after 12 months (rows stay for counts); unanswered-question text deleted after 12 months; contacts (and their conversations/messages) deleted 12 months after a client leaves (`npm run offboard-client`); a departed client's WhatsApp token wiped immediately; `admin_alerts` logs deleted after 90 days. **Backups (90 days) are managed by Supabase, not by this code:** set the retention in your Supabase project (Database > Backups) to 90 days or less, and set log retention in Vercel to match. `usage_events` (anonymous token counts) are kept.
- **Daily check** (`/api/cron/daily-check`): per client, messages received vs replies sent in the last 24h, plus conversations with no reply, failed/blocked sends and stuck batches. It emails the admin only when something is wrong.
- **Cron on Vercel:** `vercel.json` runs token refresh (03:00 UTC), retention (03:30), sweep (04:00) and daily check (07:00), each once a day, which Hobby plans allow. All cron routes require `CRON_SECRET` (16+ chars) and are safe to run twice.

## Setup

Requires Node 20.9+.

1. **Install**: `npm install`
2. **Supabase database**: create a project in the Supabase dashboard, then link it and apply the migrations with the Supabase CLI (run from this folder; `npx` downloads the CLI, it is not a project dependency):
   ```bash
   npx supabase login                                  # opens a browser to authorise the CLI
   npx supabase init                                   # once only; creates supabase/config.toml, keeps supabase/migrations/
   npx supabase link --project-ref <project-ref>       # ref = the id in https://supabase.com/dashboard/project/<project-ref>
   npx supabase db push --remote --dry-run             # preview: should list 0001 to 0015 (newer CLIs target a LOCAL stack unless you pass --remote)
   npx supabase db push --remote                       # apply to the linked project (asks for the database password you set when creating the project)
   npx supabase migration list                         # Local and Remote columns should both show 0001 to 0015
   ```
   For non-interactive use set `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD` instead of answering prompts.
   **Schema rule:** all schema changes live in numbered files in `supabase/migrations/` (`npx supabase migration new <name>` creates the next one). Never edit tables, policies or functions by hand in the dashboard. Each table is created with RLS enabled in the same migration. If you applied an earlier draft of 0001/0002 (they were reorganised before the first release), reset that database first.
3. **Supabase Auth settings** (needed for sign-up): in the Supabase dashboard open Authentication, then Providers > Email and make sure **Confirm email** is on; under URL Configuration set **Site URL** to your app URL (the same as `APP_URL`) and add `<APP_URL>/login` to **Redirect URLs**. For reliable confirmation emails at any volume, set up custom SMTP in Authentication > SMTP Settings, because Supabase's built-in email service is heavily rate limited. Then install the branded confirmation email (see "Branded emails" above). (Menu names are from memory; check them in your dashboard.)
4. **Env**: `cp .env.example .env` and fill it in (every variable is explained there). Generate the encryption key with `openssl rand -base64 32`. `GRAPH_API_VERSION` is pinned in env (Meta's docs currently show `v26.0`). In Supabase > Project Settings > API, copy the project URL, the public anon key and the service-role key.
5. **Meta app** (developers.facebook.com): create a Business app and add the **WhatsApp** product. Under *WhatsApp > API Setup* you get a **test phone number**, its **Phone number ID**, and a temporary **access token** (expires in about 24h; regenerate it and re-run step 7 when it does). Add your own phone as a recipient there.
6. **Webhook**: deploy (or tunnel), then in *WhatsApp > Configuration* set
   - **Callback URL:** `https://<your-domain>/api/webhooks/whatsapp`
   - **Verify token:** the value of `WHATSAPP_VERIFY_TOKEN`
   - click Verify and save, then **subscribe to the `messages` and `account_update` fields** (the latter confirms Embedded Signup onboardings).
   - Local testing: `npm run dev`, expose it with a tunnel (e.g. `ngrok http 3000`) and use `https://<tunnel>/api/webhooks/whatsapp`.
   - `WHATSAPP_APP_SECRET` is under *App settings > Basic > App secret*.
7. **AI keys and email**: put `GEMINI_API_KEY` (aistudio.google.com) and optionally `OPENAI_API_KEY` in `.env`. For email, turn on 2-step verification on a Gmail account, create an app password at myaccount.google.com/apppasswords, and set `GMAIL_USER`, `GMAIL_APP_PASSWORD`, `ADMIN_ALERT_EMAIL` and `APP_URL`. With these unset, emails are skipped (a warning is logged) and everything else still works.
8. **Register the test number as a client**:
   ```
   CLIENT_NAME="Test Biz" WA_PHONE_NUMBER_ID=<phone number id> WA_ACCESS_TOKEN=<token> OWNER_EMAIL=you@example.com npm run create-client
   ```
   The token is stored AES-256-GCM encrypted in `client_secrets`, a table the dashboard's database role cannot read. The command prints the client id.
9. **Create your dashboard login**: `CLIENT_ID=<id from step 7> OWNER_LOGIN_EMAIL=you@example.com OWNER_PASSWORD='a-long-password' npm run create-owner`, then sign in at `/login`.
10. **Try the eval first** (no database needed): `npm run eval` runs the 20 sample questions in `eval/questions.json` against the sample knowledge base `eval/sample-kb.md` on both providers (or `npm run eval -- --provider gemini`). It prints each reply with PASS/FAIL, tokens and latency. The checks are heuristic, so skim the replies.
11. **Give your test client knowledge**: paste the sample into dashboard > Knowledge base > Core knowledge, or run `CLIENT_ID=<id> KB_FILE=eval/sample-kb.md npm run set-kb` (optional `BOOKING_LINK=...`, `AI_PROVIDER=openai`). Try uploading a `.docx` or `.txt` under Documents to see the preview-and-confirm step.
12. **Test on WhatsApp**: message the test number several short messages in a row. You should get ONE reply about 5 seconds later, built from all of them. Check `messages` (token columns filled), `usage_events` and `pending_messages` (empty again). Replaying the same payload must not produce a second reply. Try "I want to talk to a person": you should get an owner email and the conversation shows as waiting in the dashboard.
13. **Vercel**: add the same env vars to the project (including `CRON_SECRET`; on Hobby the crons run once a day, on Pro you can make `/api/cron/sweep` run every minute). Routes that wait for the batch window or call a model set `maxDuration = 60`.

Copy its **Configuration ID** into `NEXT_PUBLIC_META_ES_CONFIG_ID`.

   - **Allowed Domains for the JavaScript SDK:** `https://YOUR-APP.vercel.app`

   - **Callback URL:** `https://YOUR-APP.vercel.app/api/webhooks/whatsapp`

### Testing Embedded Signup from your own computer
Meta's popup refuses to open from any `http://` page, including `http://localhost:3000` (you will see "The method FB.login can no longer be called from http pages"). Use an **https** address instead:
- **Easiest:** test on your deployed Vercel URL. It is stable, so the Meta settings above only need entering once.
- **Locally:** run `npm run dev` and `ngrok http 3000`, then open **the https ngrok address** (not localhost) for `/onboarding`. ## Manual test checklist: Embedded Signup in Development Mode

Needs a deployed app with all env vars set, migrations 0001 to 0015 applied, and a Facebook account that has a role on your Meta app.

1. **Create a login with no business:** use `/signup` (and approve it on `/admin/signups` only if you set `SIGNUP_MODE=approval`), or add a user in the Supabase dashboard (Authentication > Users > Add user, auto-confirm) and approve it the same way. Do *not* use `create-owner`, which links a business.
2. **Sign in at `/login`.** You should land on `/onboarding` ("Connect your WhatsApp number").
3. **Connect:** enter a business name, click **Connect WhatsApp**, finish the popup with a WhatsApp account and number you control. Expect "Connected!" and a redirect to `/dashboard`.
4. **Check the result:**
   - Dashboard banner says *waiting for WhatsApp to confirm*, then **connected** within minutes (after the `account_update` webhook).
   - In the database: one `clients` row (`status = active`, `onboarding_step = complete`), a `client_users` link, a `client_secrets` row with an encrypted token, `wa_token_expires_at` about 60 days ahead, and a `whatsapp_account_events` row `PARTNER_ADDED`. Note whether `wa_token_expiry_assumed` is true or false: that answers the first docs question.
   - You received the "Your WhatsApp number is connected" email.
5. **Use it:** add a little core knowledge in the dashboard, message the connected number from another phone, and confirm a reply.
6. **Failure and resume:** in Vercel set a wrong `WHATSAPP_APP_SECRET`, redeploy, and connect with a second fresh login. Expect a plain-language error, a `failed` banner with **Reconnect**, and `onboarding_step = token_exchange`. Fix the secret, press Reconnect, and confirm it succeeds **on the same `clients` row** (still exactly one row for that login).
7. **Duplicate protection:** with a different login, try to connect the same WhatsApp account. Expect "already connected to a different business" and no new rows. Double-click **Connect** once: expect "already in progress", not two clients.
8. **Token refresh (the unclear-docs experiment):** in the SQL editor set that client's `client_secrets.wa_token_expires_at` to `now() + interval '5 days'`, then run `curl -H "Authorization: Bearer $CRON_SECRET" https://YOUR-APP.vercel.app/api/cron/token-refresh`. Expect `refreshed: 1` and the expiry moving to about 60 days ahead. If it reports `failed: 1` you also get an email: Meta's refresh does not work for these tokens and customers will need to reconnect every 60 days.
9. **Expiry:** set `wa_token_expires_at` to a past time and run the cron again. Expect the dashboard to show *failed / please reconnect* and an admin email.
10. **Removal:** in Meta Business Settings remove your app from the WABA's connected apps. Expect `PARTNER_REMOVED`: status `failed` and an admin email.
11. **Clean up** the test client and users.

## Multi-tenancy and secrets
- Every table has `client_id`. Composite foreign keys `(id, client_id)` stop a row from pointing at another client's parent row.
- RLS is on for every table; owners can only read rows of clients they belong to via `client_users`. `client_secrets`, `admin_alerts`, `pending_messages` and `whatsapp_account_events` have RLS on with no policy and no grants, so they are unreachable from a browser session.
- The server uses the service-role key (bypasses RLS), so **every server query filters by `client_id`**. Keep `lib/supabase-admin.ts` out of client code.
- WhatsApp tokens and PINs are AES-256-GCM encrypted at rest (key from `ENCRYPTION_KEY`), never logged, never sent to the browser. The app secret and tokens are kept out of error messages (covered by tests).

The manual checklist covers all three.

## Known limits
- One business per owner login; a login with no business is sent to `/onboarding`.
- Each webhook invocation sleeps ~5s for the batch window; fine at small scale.
- Template messages (outside the 24-hour window) are not sent to customers; templates are Phase 2.
- Unsubscribing a departed client's WABA from our app is not automated; do it in Meta's dashboard when offboarding.
